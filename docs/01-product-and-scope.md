# 产品定位与范围

更新：2026-10-14。根据产品研究修订的产品设计基线；用户已确认项见 [决策记录](09-decisions-and-open-questions.md)。最新实施授权仅限 P0 恢复修复与验证；完整业务设计仍未实现，结果见 [P0 记录](validation/2026-10-14/p0/README.md)。

## 1. 产品是否有价值

适合做，尤其适合开发者自己高频使用后逐步产品化。一人公司常见问题是：事情同时很多、上下文散落、跨工具操作重复、执行过程不透明、完成标准模糊。把这些问题连成一个完整工作流程，比增加一个聊天入口更有价值。

建议一句话定位：**把事情交给你的 AI 团队，随时看进展、接管决策、验收成果。**

机会在四处：

- 岗位长期存在，职责、工具和经验可以积累；每个任务又有独立上下文。
- 用户能看到任务在做什么、为什么停住、需要自己决定什么。
- 一套本地工作区可备份和迁移，不把核心业务状态交给单一模型厂商。
- 同一套流程覆盖办公、研发与经营，切换的是模板和能力组合。

这不是已经证实的市场空白。Paperclip 已涉及组织与任务协作，WorkBuddy 已提供办公执行体验，多个开源 Agent 已有模型、工具与会话机制。应通过真实任务验证“更省事、更可控”是否成立。[参考研究](research/business-knowledge-references.md)、[WorkBuddy 官方介绍](https://www.workbuddy.cn/)。

建议先让自己与 3–5 位目标用户连续使用两周，记录每周完成任务数、返工时间、人工接管次数、模型成本、第二周复用率。用户是否愿意把同类工作持续交给它，比演示里有多少 Agent 更有说服力。收费方式暂不冻结。

## 2. 核心概念

| 概念 | 用户理解 | 系统职责 |
| --- | --- | --- |
| 工作区 Workspace | 我的公司资料和工作环境 | 本地数据边界、共享能力、设置与备份 |
| 模式 Mode | 现在做办公／研发／经营 | 推荐岗位、工具、流程、成果类型与默认页面 |
| 岗位 Role | 调研员、开发者、编辑等职责 | 可复用的职责和验收模板 |
| Agent | 担任岗位的一个 AI 同事 | 有稳定身份、能力绑定和私有经验的配置实例 |
| 临时子 Agent | 为一次分工安排的助手 | child Run 的受限执行身份，不自动创建长期成员；任务责任仍有人承担 |
| 项目 Project | 一组要持续推进的事情 | 目标、需求、任务、资料和成果 |
| 需求 Requirement | 想达到什么结果 | 背景、约束、验收标准与预算 |
| 任务 Task | 一项可分派、可验收的工作 | 责任人、依赖、状态和交付要求 |
| 对话 Conversation | 与某人讨论一件事 | 消息与上下文；可关联任务，也可独立聊天 |
| 执行 Run | 某次实际开始干活 | 模型调用、工具调用、暂停点、预算与结果 |
| Attempt | 中断后的一次实际运行尝试 | Worker、租约和执行资格；安全续接仍属于原 Run |
| Operation | 一次具体工具动作 | 稳定操作 ID、固定参数、批准、回执与对账 |
| 成果 Artifact | 可使用的文件或外部结果 | 版本、来源、校验信息、验收记录 |

岗位不等于操作系统进程；Agent 不等于会话；一个 Agent 可以有多个独立 Run，同一岗位可以由多个 Agent 担任。这样既保留职场模型，也不会给每个头像常驻一个进程。

产品入口先交办任务。纯问答可独立聊天；开始工具执行、后台工作或委派时自动建立轻量 Task，未选项目的任务放在收件箱。岗位、模型和连接器在需要时提供模板或补齐入口，不要求用户先搭好组织再工作。

## 3. 三模式共用内核

| 模式 | 最小岗位模板 | 第一版完整场景 | 完成依据 |
| --- | --- | --- | --- |
| 办公 | 助理、调研员、编辑／复核员 | 读取指定资料与网页，形成带引用的调研报告，复核后发送汇报 | 文件可打开、引用可追溯、缺失信息明确、审批与发送结果可查 |
| 研发 | 需求分析、开发、测试／审查 | 从需求拆任务，在指定仓库隔离修改，运行检查并生成交付说明 | 可审查的差异、命令退出码、测试结果、未验证项；默认不自动合并或发布 |
| 经营 | 运营、客户助理、分析／复核员 | 基于用户提供的产品与客户资料产出内容或跟进草稿，授权后发送／更新 | 有来源、符合模板、收件人和范围可核对、对外结果可追踪 |

模式切换不迁移数据，不清空记忆，不修改运行中任务。项目有默认模式，任务可覆盖；跨模式任务通过依赖串联。新建任务时固定模式模板版本，后续编辑不改变已开始的 Run。

第一版三种模式都必须有可用闭环；它们不意味着第一版自建 IDE、CRM 和完整办公套件。现成工具通过统一扩展层接入，产品只负责协调、成果与状态。

## 4. 需求覆盖

| 用户需求 | 设计归属 | 第一版范围 |
| --- | --- | --- |
| 多厂商、多协议、自定义 API、Embedding UI | 模型连接管理 | 指定供应商预设与协议适配，逐连接检测能力；独立 Embedding 设置 |
| Agent loop | MAF + 执行适配层 | 工具循环、预算、取消；分别验证历史恢复、界面重连、运行续接和副作用对账 |
| 多 Agent | 任务调度器 + MAF 运行器 | 长期责任人与临时执行身份分开；持久子任务、交接、依赖和复核 |
| Chat 与历史 | 会话模块 | 流式对话、搜索、继续、关联任务、基础分支 |
| Skills、MCP、插件按 Agent 分配 | 能力中心 | 共享库、Agent 引用、启停、连接检查、兼容性提示 |
| 分层记忆、冷热、共享 | 记忆模块 | 工作上下文、经历、事实和岗位经验分开；候选发布、版本、冷热、纠错和撤回 |
| RAG 知识库 | 资料模块 | 导入、解析、混合检索、引用、重建、失败重试 |
| 岗位身份与自动创建 | 岗位模板 + Agent 注册 | 按受限模板临时委派；长期成员单独建立并选择可发布经验，不复制全部临时历史 |
| 需求任务面板、API/webhook | 项目模块 | 列表／看板、依赖、状态机、鉴权和幂等接单 |
| SMTP 阶段汇报 | 通知模块 | 开始、阻塞、待确认、完成、定期摘要，可选收件人 |
| Dashboard | 工作台与执行事件 | 状态、阶段、当前动作、费用、阻塞与待处理事项 |
| 亮色、毛玻璃、非技术化体验 | React 界面 | 简单表单、渐进展开、清晰操作与恢复入口 |
| OPC、简化权限 | 单所有者模型 | 无企业 RBAC；保留登录、工具授权、外发确认 |
| 文件、共享与私有目录 | 工作区管理 | 配置／知识／长期记忆为文件，SQLite 主存任务和对话 |
| 核心 AOT、扩展独立进程 | Host/Worker 边界 | 核心 AOT 发布门槛，非兼容依赖留在 Worker |
| Windows/macOS/Docker | 部署模块 | 单机单工作区运行，同一浏览器界面 |

## 5. 必须增加的产品约束

这些约束是让已提出的能力可长期使用所需的设计，不是额外的企业治理系统。

1. 每项任务有验收标准、预算、超时和结果存放位置。
2. 有暂停、取消、重试、转交和人工接管；暂停与取消的含义不同。
3. Agent 提议创建任务与修改正式状态，要经过服务端规则检查。
4. 拿不到工具、凭据或资料时明确阻塞，不生成虚假的完成状态。
5. 网络超时后的外部动作可能已经成功，必须先核对再决定重试。
6. 备份包含主数据库、权威文件与必要凭据恢复材料，不能只备份配置。
7. 模型成本有每日和单任务上限；无法获得实际 token 时显示估算。
8. 模型更换、插件升级和文件修改不能悄悄改变正在执行的任务。

Task 完成必须有对应 revision 和成果版本的验收记录。工具成功但最终回复失败时保留真实成功回执；成员改派先停止/核对旧写者再切换责任。岗位经验经显式发布才共享，检索命中和压缩摘要不能直接变成长期事实。完整规则见 [04 协作](04-agent-harness-and-projects.md)、[06 记忆](06-memory-and-knowledge.md)、[13 恢复](13-restart-and-recovery.md)。

## 6. 暂不进入第一版

桌面鼠标键盘控制、原生桌面壳、多租户与复杂部门权限、分布式调度、自训练模型、完整 GraphRAG、自动无限增员、全厂商所有高级特性的等价支持、所有 Codex／Claude／Pi 插件的无差别运行。

后续扩展必须基于明确使用场景。比如用户频繁需要操作没有 API 的桌面软件时，再加入桌面执行器；需要多台机器协作时，再研究远程 Worker。
